# KinoBot Production Deployment Runbook

The supported production runtime is Docker Compose. The API process also runs Telegram polling; there is no separate bot or PM2 process. On a prepared Debian/Ubuntu server, a deploy normally takes 30-60 minutes depending on image downloads, build speed, and database size. The installer and deployer do not guarantee that duration.

## Requirements

- Fresh Debian 12+ or Ubuntu 22.04+ server, at least 2 vCPU, 4 GB RAM, and 20 GB free disk recommended.
- DNS A record for the production domain pointing to this server.
- Inbound TCP 80/443 open for ACME certificate issuance and HTTPS; SSH restricted to operator IPs.
- Source archive or Git checkout for `feature/actor-card-mvp`.
- A valid email for Let's Encrypt and a PostgreSQL admin password with 16+ alphanumeric characters.

### Reported Test Server

The following baseline was supplied in the deployment test notes and has not
been independently queried by this workspace:

- AWS EC2 `t3.small`, Ubuntu 24.04 LTS, 2 vCPU.
- 1.9 GB RAM with 2 GB swap; 29 GB disk with 26 GB free at test time.
- Domain `3-27-225-225.sslip.io`; Let's Encrypt certificate expiry reported as
  2027-01-25.
- Docker 29.9.2 and Node.js 22.
- Reported first deploy about 4 minutes; repeat deploy about 2 minutes.
- Reported post-deploy state: 6 roles, 41 tables, 10 genres, 4 plans, and 1
  admin account.

These are observed test values, not sizing guarantees. A production workload
with simultaneous builds may require more than the tested 1.9 GB RAM.

The Compose stack includes PostgreSQL, Redis, a bootstrap/backup/migration/seed job, the API, dashboard (its own Nginx), and the public Nginx reverse proxy. Host PostgreSQL, host Nginx, and PM2 are not required.

## First Installation

1. Copy/extract the complete source checkout or ZIP onto the server. Keep `.env`, TLS private keys, backups, logs, and `node_modules` out of the archive.
2. Verify the source is the intended release branch/commit. For Git:

   ```bash
   git branch --show-current
   ```

3. Run the installer from the source root or its `scripts` directory:

   ```bash
   sudo bash scripts/install.sh
   ```

   It installs Docker Engine/Compose, Node.js 22, pnpm 9.15, Git, curl, unzip, rsync, OpenSSL, and Certbot; copies source to `/opt/kinobot`; and creates a mode-600 `.env` from `.env.example` if one is not already present. It prompts for the domain, PostgreSQL admin password, and optional JWT access secret; other high-entropy secrets are generated with OpenSSL.

4. Installer requests a Let's Encrypt certificate in standalone mode. DNS must already resolve to the server and port 80 must reach it. If issuance is not possible, stop and arrange valid certificate/key paths in `.env` before deployment.
5. Edit `/opt/kinobot/.env` and set `ADMIN_TELEGRAM_IDS` to numeric Telegram user IDs. Add payment secrets only for providers that are enabled. Do not put `.env` or private keys in ZIP/Git/chat.
6. Configure the Telegram bot token in the dashboard/admin settings after first deploy. Bot polling is enabled in the API with `TELEGRAM_POLLING_ENABLED=true`.
7. Run the first deploy:

   ```bash
   cd /opt/kinobot
   sudo bash ./scripts/deploy.sh
   ```

   For an uploaded source ZIP instead of Git:

   ```bash
   sudo bash ./scripts/deploy.sh /opt/releases/kinobot-release.zip
   ```

The deploy script performs a verified pre-migration `pg_dump` to
`/opt/kinobot/backups`, then starts database bootstrap, migration, RBAC seed,
application seed, API, dashboard, and Nginx in order. It builds workspace
artifacts and Docker images. It fails on the first unsuccessful command and
prints recent Compose logs. Shell scripts are tracked as mode `100644`, so use
`bash scripts/deploy.sh`; do not `chmod` tracked checkout files. Installer-copied
source intentionally has no `.git`; the deployer recognizes that staged tree.
Pass a new ZIP path to deploy an updated archive.

## Environment and Database Roles

- `DATABASE_URL` is the runtime app login `kinobot_user`; its password is generated by the installer.
- `MIGRATION_DATABASE_URL` is the local PostgreSQL administrator login used only by DB bootstrap, backup, and the migration container. Do not use it as the API URL.
- PostgreSQL data persists in the `postgres_data` named volume. Redis state persists in `redis_data`; uploads persist in `upload_data`.
- `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, and `SESSION_SECRET` are distinct random values. Do not rotate them casually; doing so invalidates sessions/tokens.
- `CORS_ORIGINS` is an exact HTTPS origin such as `https://kino.example.com`, without a trailing slash or path. Wildcard `*` is rejected. Dashboard API requests use same-origin `/api` routing.
- `TLS_CERT_FILE` and `TLS_KEY_FILE` point to the host certificate and private key. Installer uses Certbot paths under `/etc/letsencrypt/live/<domain>/`.
- `TELEGRAM_POLLING_ENABLED=true` starts polling in the API process. The API exposes permission-protected `/api/telegram/bot/start` and `/api/telegram/bot/stop` controls; the dashboard action invokes the API, not a second process.
- `ADMIN_TELEGRAM_IDS` must be set before deployment. `SUPER_ADMIN_*` bootstrap values are optional; leave blank unless the project seed flow is explicitly configured for initial admin creation.

The API binds to `0.0.0.0` inside its container so Docker networking works, but Compose publishes the API only on host loopback (`127.0.0.1:8080`). Public requests go through the Nginx container on ports 80/443. Do not change the in-container host binding to `127.0.0.1`.

## Migration 0008

`0008_audit_owner_separation.sql` creates/configures audit roles, transfers ownership of audit tables, and restricts application/archiver grants. Those are privileged PostgreSQL operations. The migration runner applies pending migrations transactionally and verifies migration hashes.

Do **not** catch `insufficient_privilege`, emit only `NOTICE`, and continue to stamp 0008 as applied. If role creation or ownership changes were skipped, the ledger would say the security migration completed while audit tables may remain owned by the app role; owner privileges bypass ordinary `REVOKE` statements. A missing role also makes the later grants fail. Therefore the production migrator must have the needed rights. The included self-hosted Compose deployment uses the PostgreSQL admin URL for this job while the API connects as the restricted app role.

For managed PostgreSQL, use the provider's approved DBA role/provisioning procedure and test against a restored staging copy first. If that provider cannot perform the role/ownership changes, the current 0008 is not compatible with that privilege model as-is. Do not edit an already-applied migration: its SHA-256 is stored in the ledger. Design and review a new forward migration or a provider-specific DBA procedure, reconcile the ledger deliberately, then deploy. Never run only selected SQL statements and leave the ledger unaware of them.

Deploy sequence for database changes:

1. The deployer starts PostgreSQL/Redis and the privileged `db-init` creates
   the app role plus `audit_owner` and `audit_archiver` before migration.
2. It creates a custom-format backup and checks it with `pg_restore --list`.
3. It runs `assert-migration-state.mjs`, then the canonical `migrate-live.mjs` migrator.
4. Migration `0011` creates the base roles if missing and links the health
   permission to admin and superadmin. The `db-seed` job then runs
   `seed-roles-permissions.ts` before optional admin bootstrap and catalog seed.
5. Only after migration and seed success do application services start.

The role/permission seeder is deliberately independent of optional
`SUPER_ADMIN_EMAIL` and `SUPER_ADMIN_PASSWORD`; an empty admin-bootstrap config
does not suppress role and permission initialization.

## Nginx, TLS, and PM2

The public Nginx container publishes 80/443 and reverse-proxies `/api` to the API service and other paths to the dashboard. The dashboard container separately serves the Vite build with SPA fallback. No host Nginx installation or checked-in `dist/public` is needed; Docker builds the dashboard image from source.

Let's Encrypt certificates renew on the host. After a successful renewal, restart the proxy so it reopens the certificate files:

```bash
sudo certbot renew
cd /opt/kinobot && sudo docker compose -f docker-compose.prod.yml restart nginx
```

PM2 is not part of this deployment. Do not start a separate bot process while API polling is enabled; duplicate polling sessions can conflict. If running API replicas, ensure only one instance polls Telegram or disable polling on all but one intentionally selected instance.

## Troubleshooting

- **Installer says unsupported OS or apt package failure:** use Debian/Ubuntu, check outbound HTTPS and DNS, and rerun after fixing apt repository access.
- **Let's Encrypt validation fails:** verify the A record, security group/firewall TCP 80, and that no other process owns port 80. Fix DNS/network, then rerun Certbot for the configured domain.
- **Compose config reports a missing variable:** check `/opt/kinobot/.env`; required database URLs, passwords, JWT/session secrets, CORS origins, TLS paths, and admin Telegram IDs must be present. Do not source `.env` into a shell.
- **CORS error:** ensure the browser's exact origin is present in `CORS_ORIGINS` with `https://`, no trailing slash/path, and restart/redeploy API after changing `.env`.
- **Migration 0008 fails with permission denied:** inspect `docker compose -f docker-compose.prod.yml logs db-migrator`; confirm the migration URL has provider-supported role and ownership privileges. Do not suppress the error or mark the migration applied manually.
- **Migration hash mismatch:** the deployed SQL differs from the version recorded in the DB ledger. Restore the exact release migration files or prepare an approved forward reconciliation; do not edit the applied migration.
- **Dashboard/API is unavailable:** check `docker compose -f docker-compose.prod.yml ps` and `logs --tail=100 api-server dashboard nginx`; confirm ports 80/443 are open. Local health endpoints are `http://127.0.0.1:8080/api/healthz` and `http://127.0.0.1:3000/health`.
- **Bot does not start:** confirm `TELEGRAM_POLLING_ENABLED=true`, an active token is configured in the admin UI/database, outbound Telegram connectivity works, and logs show bot startup. The API can start without a configured bot token.
- **DB bootstrap authentication failure:** confirm `POSTGRES_USER`, `POSTGRES_PASSWORD`, and `MIGRATION_DATABASE_URL` agree. Existing named volumes retain their initialized credentials; changing `.env` does not reset a PostgreSQL volume password.
- **API log `EACCES`:** the installer assigns `/opt/kinobot/logs/api` to UID/GID 1001, matching the API container's non-root user. If the directory was created earlier, repair its ownership during an approved maintenance window.
- **Redis overcommit warning:** installer enables `vm.overcommit_memory=1` immediately and persists it in `/etc/sysctl.d/99-kinobot-redis.conf`.
- **Missing SSL README / Git checkout marked dirty:** installer excludes `.git/` and only excludes TLS `.pem` files from copies, preserving `nginx/ssl/README.md`. It does not chmod tracked scripts.
- **No RBAC roles or missing health permission:** check the 0011 migration ledger row and `db-seed` logs. The application permission map includes `view:health` for admin and superadmin; the DB seeder must finish after migrations.
- **Disk space or backup failure:** inspect `/opt/kinobot/backups` and free space. Backups contain production data; retain restricted permissions and move copies to approved encrypted storage. The script does not automatically delete old backups.

## Operational Commands

```bash
cd /opt/kinobot
sudo docker compose -f docker-compose.prod.yml ps
sudo docker compose -f docker-compose.prod.yml logs --tail=100
sudo docker compose -f docker-compose.prod.yml restart api-server dashboard nginx
curl --fail https://<domain>/api/healthz
curl --fail https://<domain>/health
```

The deploy automation, installation, and documentation do not replace staging validation, monitoring, encrypted off-host backups, or a tested restore/rollback procedure.
